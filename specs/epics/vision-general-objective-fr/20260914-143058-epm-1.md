## Shared Approach

One Spring Boot module, one jar, layered internally (controller → service → repository), organized
package-by-feature per `GUARDRAILS.md` G2.1/G2.7. Five business modules —
`booking`, `pricing`, `eventmanagement`, `availability`, `quote` — do not import each other
(G2.3); they communicate through domain events (for the two eventually-consistent public
projections) or an explicit synchronous read contract (for the correctness-critical purchase path
— see "Cross-Cutting Constraints" below, this rule is load-bearing and stated explicitly because
G2.3's phrasing alone does not disambiguate which style applies where). A sixth package area, `web`
(BFF + customer-facing UI composition), sits above the five business modules and is the only area
allowed to call into more than one of them.

## Shared-File / Shared-Concept Ownership

No source files exist yet — this is a planning task. Ownership is fixed at the module/package
level (Domain Boundaries table above); exact file paths within each package are assigned by the
architecture and code-planning stages, which must respect these package boundaries and must not let
two capabilities write into the same package's guarded-SQL/state-machine code (see NFR-000-1 under
EP-003 — the single shared Reservation state machine). The only same-directory-writer risk
identified at this planning altitude is exactly that one: CAP-005/CAP-006/CAP-007 all mutate the
same `booking` aggregate. It is called out as a cross-cutting constraint below rather than resolved
by merging the three capabilities, because they remain independently boundable units of user-facing
behavior (three different Story Writer briefs) even though their persistence mechanism is one
contract, not three.

## Cross-Cutting Constraints

Binding on every epic below, restated here because they are easy to lose at the capability level:

- **G0.1/G0.2** (secrets, parameterised SQL) and **G1.1–G1.6** (authorisation, no
  server-controlled field from the body, typed errors, security headers/CSP, least-privilege DB
  account, CSRF) apply to every write capability without exception — see vision-general-objective-fr.md:533-561
  which restates the same list as a release gate.
- **Synchronous vs. asynchronous boundary is load-bearing, not incidental.** `booking`'s checks
  against `eventmanagement` (seat sellability) and `pricing` (authoritative price) MUST be a
  synchronous explicit read contract. `GUARDRAILS.md` G2.3 allows "domain events or an explicit
  read contract" without saying which applies where; if a downstream architect defaults to
  events for both directions (mirroring how `availability`/`quote` are built), the "no
  double-booking" and "never charge a lagging price" guarantees silently degrade to eventual
  consistency. Only the write→`availability`/`quote` direction is event-based.
  (Systemic Decomposition Review, finding 3.)
- **One shared Reservation state machine.** CAP-005, CAP-006, CAP-007 share one guarded,
  single-SQL-statement mechanism over one `held → confirmed → {expired|cancelled}` state machine
  (vision-general-objective-fr.md:94-98, 116-128). Whichever capability's Story Writer/architect
  designs the guard first fixes the schema for the other two — this must be a stated shared
  contract in the architecture stage, not three independently re-derived mechanisms.
  (Systemic Decomposition Review, finding 2.)
- **Amounts** are integer minor units end-to-end, no floating point, in every capability that
  touches money (CAP-003, CAP-004, CAP-006, CAP-007, CAP-012, CAP-013).
- **Every endpoint declares exactly one access level** (public / client authentifié / organisateur
  / opérateur) per vision-general-objective-fr.md:177-192 — an undeclared level is treated as a
  build-time error in every capability, not a silent public route.

## Systemic Decomposition Review

Analysis run via the `systemic-thinking` skill against this draft decomposition before
`set-task-output`. Two findings below changed the plan (noted inline); the rest are recorded
as-is per the skill's "no fixes, name what you see" discipline — disposition is the Orchestrator's
call at the next planning cycle.

**[BLIND SPOT] Orphaned-confirmed-reservation recovery was initially scoped to CAP-005 (Hold).**
Recovering a confirmed reservation left behind by a purchase that crashed mid-flight requires
knowledge of CAP-006's transaction boundary — a boundary that does not exist yet when CAP-005 is
designed and built (CAP-005 precedes CAP-006 in dependency order). Assigning this recovery to
CAP-005 would have built the purge mechanism ignorant of the failure mode it must reverse.
Implication: the "failed purchase leaves no trace" invariant would be enforced by code written
before its counterpart exists.
**Resolution applied:** orphaned-confirmed-reservation recovery moved into CAP-006's scope;
CAP-005 now owns only expired-hold reclaim. Recorded as ASM-005-1 (Confidence: MEDIUM — flagged
Verify: Yes in EP-003's Interpretation Decisions, since a single unified purge capability is a
reasonable alternative reading).

**[LOAD-BEARING] The three-way split of Hold/Purchase/Cancellation understates how tightly the
concurrency mechanism binds them.** The vision specifies one guarded single-statement SQL family
and one Reservation state machine across all three. Treating them as independently boundable Story
Writer briefs is correct for user-facing behavior, but without an explicit cross-capability
contract, whichever is designed first silently fixes the schema for the other two.
**Resolution applied:** stated explicitly as a Cross-Cutting Constraint above and as NFR-000-1 in
EP-003, rather than left implicit.

**[TENSION] `GUARDRAILS.md` G2.3 permits "domain events or an explicit read contract" between
business modules without a scope rule for which applies where.** The purchase/hold path needs
synchronous reads (no staleness tolerated); the public-projection path needs and explicitly
tolerates asynchronous eventual consistency (vision-general-objective-fr.md:166-173). A downstream
architect who infers one project-wide communication style from the guardrail's either/or phrasing
would weaken a correctness guarantee that the vision treats as non-negotiable.
Implication: recorded as a Cross-Cutting Constraint above; not a plan change, since the fix is
architectural documentation, not a re-boundary.

**[FRAGILITY] No capability owns reconciliation of a partial failure between the local guarded
write and the external Payment Gateway** (gateway refunds but the local cancel-write fails to
commit, or the reverse). The gateway interface (authorize/void/refund) is not described as safe to
retry blindly, and the vision's idempotence requirement covers client-visible replay, not
gateway/local desynchronization.
Implication: recorded as OQ-000-1 in EP-003 — neither CAP-006 nor CAP-007 can fully bound its
"no trace on failure" criterion without an answer; not resolved by assumption because it is a
genuine design gap, not an ambiguity.

**[ASSUMPTION] The seat block/unblock access-level contradiction (vision's "Utilisateurs cibles"
assigns it to Opérateur; "Contrôle d'accès" is silent on it for Opérateur and only grants
Organisateur "toutes les écritures d'événement") does not stay contained to EP-001.** EP-003's
hold/purchase guards consume seat sellability regardless of which role produced it, and EP-006's UI
must render "not for sale" correctly regardless of cause. An unresolved access-level question in
CAP-002 propagates to every consumer of seat-sellability, not just its own epic.
Implication: recorded as OQ-000-1 in EP-001, with impact text naming the downstream propagation
(not just a local EP-001 concern).

**[TRAJECTORY] The module=capability=epic 1:1 ownership model has no declared seam for future
capabilities.** The vision's own "Risques, hypothèses et questions ouvertes" section names likely
post-MVP asks (per-seat pricing, discount codes, multi-seat carts, waitlists) that do not obviously
nest inside any of the six modules above without renumbering the dependency graph.
Implication: acknowledged, no plan change — matches the vision's own explicit MVP deferral of these
features; the Orchestrator can decide at the next planning cycle whether to reserve seam capacity.

# Epic EP-001: Event and Seat Inventory Management

Status: draft

---

## Part 1 — Intent Review

### Promise

**Before this epic:** There is no way for an organizer to put an event and its seats up for sale,
or for anyone to take a seat out of and back into circulation.

**After this epic:** An organizer can take an event from a draft through seat setup to being open
for sale, or cancel it outright and irreversibly. A seat can be individually taken out of sale and
reinstated.

### Capability Map

| Capability | Human-facing outcome | Source intent captured | Main exclusion |
|---|---|---|---|
| CAP-001 — Event Lifecycle Management | Organizer can create, open, and cancel an event, each exactly once where the vision requires it | vision-general-objective-fr.md:42-44, 81-83 | Seat-level operations (CAP-002) |
| CAP-002 — Seat Inventory Management | Organizer can add seats with a fixed tier; a seat can be blocked/unblocked individually | vision-general-objective-fr.md:42-44, 84-87 | Definitive catalog removal ("retiré" state) |

### Interpretation Decisions

| Source signal | Epic interpretation | Confidence | Verify? |
|---|---|---|---|
| "Un état `retiré` est réservé à un retrait définitif du catalogue" | Definitive removal is explicitly out of scope for this epic; only `disponible ↔ bloqué` is covered | HIGH | No |
| "Opérateur... retire et réintègre des sièges" (Utilisateurs cibles) vs. "Contrôle d'accès" being silent on this for Opérateur | Treated as an unresolved contradiction (OQ-000-1), not silently decided in either direction | HIGH | Yes |

### Review Questions

- [ ] Should seat block/unblock be reserved to Opérateur, to Organisateur, or to both? (OQ-000-1)
- [ ] Is definitive seat removal from the catalog truly out of MVP scope, or does a minimal
      operation need to exist?
- [ ] Should modifying an event already "en vente" (e.g. adding a seat) be rejected, or remain
      possible?

## Part 2 — Execution Contract

### Goal
An organizer can take an event from draft to on-sale or cancellation, and manage its seat
inventory, with every transition guarded against double-execution.

### Context
This is the foundation every other epic reads from: nothing can be priced, held, purchased, or
projected publicly until an event and its seats exist. vision-general-objective-fr.md §"Objectif et
périmètre du MVP" item 1.

### Personas
- **Organisateur (admin)**: opère depuis une console d'administration (livrable séparé, non décrit
  dans cet epic) ; agit surtout avant l'ouverture à la vente ; attend des règles d'inventaire
  strictes et des erreurs explicites plutôt que des comportements silencieux.
- **Opérateur**: intervient en heures de service pour maintenir l'inventaire sain ; opère depuis les
  mêmes API/outils que l'admin (pas d'IHM dédiée décrite ici) ; a besoin d'actions sûres à
  ré-essayer.

### General Information

Applies to: the entire epic scope.

#### References
- spec: vision-general-objective-fr.md:26-27 (Utilisateurs cibles), :42-44 (MVP item 1), :81-83
  (Événement), :84-87 (Siège), :175-192 (Contrôle d'accès)
- plan_ref: this document, "Master Decomposition" section above

#### Epic Dependencies
None — foundational.

#### Completion Criteria
Un organisateur peut créer un événement en brouillon, y ajouter des sièges avec palier tarifaire,
l'ouvrir à la vente (une seconde tentative d'ouverture est refusée), et l'annuler (opération
terminale et idempotente qui ne se propage pas aux sièges/réservations). Un rôle habilité (portée
exacte à trancher, OQ-000-1) peut bloquer un siège individuel puis le débloquer.

#### Non-Functional Requirements
- NFR-000-1: Toute écriture de statut d'événement ou de siège est un SQL gardé en une seule
  instruction — pas de vérification-puis-écriture en deux temps.
- NFR-000-2: Chaque endpoint déclare exactement un niveau d'accès ; aucune route sans déclaration.
- NFR-000-3: Toute erreur connue (événement/siège introuvable, transition invalide, ré-ouverture
  d'un événement déjà en vente) renvoie un résultat typé, jamais une erreur serveur générique.

#### Out of Scope
Consoles d'administration/opérateur (IHM — livrable distinct) ; tarification (EP-002) ;
pré-réservation/achat/annulation (EP-003) ; retrait définitif du catalogue (état "retiré", non
spécifié par la vision) ; plans de salle / modélisation de lieu au-delà d'un nom libre et de
libellés section/rang/numéro.

#### Assumptions
- **ASM-000-1**: Le nom de lieu et les libellés section/rang/numéro sont des chaînes libres, sans
  validation de plan de salle. — *Why*: explicitement hors périmètre (vision-general-objective-fr.md:67-68).
  Confidence: HIGH.

#### Open Questions
- **OQ-000-1**: Quel niveau d'accès peut bloquer/débloquer un siège ? "Utilisateurs cibles" assigne
  cette action à l'Opérateur ; "Contrôle d'accès" ne liste pour l'Opérateur que la purge des
  pré-réservations et attribue à l'Organisateur "toutes les écritures d'événement" sans trancher si
  bloquer un siège en fait partie. *Impact if unresolved*: l'endpoint ne peut pas déclarer un
  niveau d'accès unique (violation de la règle "toute opération déclare exactement un niveau
  d'accès"), et l'ambiguïté se propage à EP-003 (consommateur de la sellabilité) et EP-006
  (doit afficher pourquoi un siège n'est pas en vente) sans qu'aucun des deux puisse la résoudre
  localement.

| Source signal | Epic interpretation | Confidence | Verify? |

## Part 2 — Execution Contract

### Goal
An organizer can establish and change the authoritative price for any (event, tier), with every
concurrent change resolved without silent data loss.

### Context
Pricing is read synchronously by the purchase path (EP-003) and projected asynchronously to the
public (EP-004); it must be correct and versioned before either can be built against it.
vision-general-objective-fr.md §"Objectif et périmètre du MVP" item 2.

### Personas
- **Organisateur (admin)**: opère depuis une console d'administration (livrable séparé) ; change les
  prix surtout avant et pendant la période de vente ; attend un refus visible en cas de collision,
  jamais un écrasement silencieux.

### General Information

Applies to: the entire epic scope.

#### References
- spec: vision-general-objective-fr.md:45-46, 88-91 (Palier tarifaire), 92-93 (Prix), 155-164
  (Tarification), 166-169 (prix faisant autorité)
- plan_ref: this document, "Master Decomposition" section above

#### Epic Dependencies
None — pricing does not verify event existence (vision-general-objective-fr.md:163-164).

#### Completion Criteria
Un organisateur peut fixer un prix absolu pour un (événement, palier), l'ajuster d'un pourcentage
avec arrondi half-up, et obtenir le prix courant faisant autorité pour ce couple ; deux changements
simultanés sur le même couple ne s'écrasent jamais silencieusement — l'un des deux échoue
visiblement. L'historique complet des versions est consultable.

#### Non-Functional Requirements
- NFR-000-1: Les montants sont des unités mineures entières de bout en bout ; aucun flottant.
- NFR-000-2: Une version de prix est allouée au plus une fois par (événement, palier) ; la collision

- NFR-000-3: L'arrondi d'un ajustement en pourcentage est half-up à l'unité mineure entière.

Tarification par siège, remises, codes promo (explicitement hors périmètre vision) ; consommation

- **ASM-000-1**: Il n'existe pas de prix implicite par défaut pour un (événement, palier) tant

  adjust (relatif au prix courant), jamais de valeur initiale implicite. Confidence: HIGH.

None at epic level.

## Capability CAP-011 - Session and Access Management

Permet à un client de se connecter via l'IdP sans jamais voir ni saisir de mot de passe dans
l'application, de conserver sa session en cas d'expiration, de se déconnecter, et empêche la
navigation vers un écran hors de son rôle.

### References
- spec: vision-general-objective-fr.md:202-224, 390-397, 488-499

### Description
Se connecter redirige (via le BFF) vers l'IdP ; le navigateur revient sur une session same-origin
sans jeton. En cours de tâche, une session expirée est rafraîchie silencieusement quand possible,
sinon le client est renvoyé à l'IdP puis ramené sur son écran d'origine avec son contexte préservé.
Se déconnecter efface la session locale et déclenche le single logout. Toute tentative d'atteindre
un écran hors du rôle du client affiche "vous n'avez pas accès".

# Epic EP-006: Authenticated Reservation and Purchase Journey (Web)

Status: draft

---

## Part 1 — Intent Review

### Promise

**Before this epic:** An authenticated customer has no screen to hold a seat, watch it count down,
buy it with full financial clarity, or manage/cancel their bookings.

**After this epic:** An authenticated customer can hold a seat, watch a live countdown, buy it
seeing the exact amount before any charge, receive a matching ticket/receipt, and later view or
cancel their bookings for a confirmed full refund — all safe to retry and never double-charging.

|---|---|---|---|
| CAP-012 — Reservation and Purchase Journey UI | Customer holds, watches countdown, and buys with full financial clarity | vision-general-objective-fr.md:245-343 (Écrans 2-4) | Post-purchase management (CAP-013) |
| CAP-013 — My Reservations and Cancellation UI | Customer views bookings, re-downloads receipts, cancels for refund | vision-general-objective-fr.md:344-362 (Écran 5) | The purchase itself (CAP-012) |

## Part 2 — Execution Contract

### Goal
An authenticated customer can complete the full hold → buy → manage/cancel journey with explicit
financial disclosure at every step and idempotent behavior under retry, refresh, or lost network.

### Context
The commercially critical surface of the platform — the vision calls the purchase screen "l'écran
critique pour la confiance". Sits entirely behind EP-005's session boundary and calls EP-002/EP-003
synchronously. vision-general-objective-fr.md §"Interfaces utilisateur (côté client)", Écrans 2-5.

### Personas
- **Client authentifié**: sous pression temporelle (compte à rebours de pré-réservation) ; ne doit
  jamais être laissé dans l'incertitude sur un débit ; utilise aussi bien mobile que desktop.

### General Information

Applies to: the entire epic scope.

#### References
- spec: vision-general-objective-fr.md:245-362 (Écrans 2-5), 364-387 (Décisions d'IHM transverses),
  412-447 (Accessibilité, UX et résilience)
- plan_ref: this document, "Master Decomposition" section above

#### Epic Dependencies
- EP-002: price display at checkout (CAP-004).
- EP-003: hold, purchase, and cancellation APIs (CAP-005, CAP-006, CAP-007).
- EP-005: an established, role-checked session (CAP-011) before any authenticated action.

#### Completion Criteria
Un client peut pré-réserver un siège, suivre le compte à rebours, l'acheter en voyant le montant
exact avant tout débit, et voir un billet/reçu dont le montant est égal à celui affiché avant
confirmation. Perdre le réseau pendant la confirmation ne produit jamais de double débit ; au
rechargement, l'issue réelle est montrée. Annuler une réservation affiche une confirmation de
remboursement ; répéter l'annulation affiche "déjà annulée" sans second remboursement.

#### Non-Functional Requirements
- NFR-000-1: Résilience — aucune action n'est optimiste (succès affiché seulement après confirmation
  API) ; rafraîchissement, retour, et nouvelles tentatives réseau ne produisent jamais de double
  pré-réservation, double débit ou double remboursement ; chaque écran indique explicitement si un
  montant a été prélevé.
- NFR-000-2: Amounts — toujours en unités mineures entières côté API, formatés selon la locale côté
  affichage, jamais un entier brut montré au client.
- NFR-000-3: Accessibilité — cible WCAG 2.1 AA, y compris annonce du compte à rebours à des seuils
  significatifs (pas à chaque tic).

#### Out of Scope
Fixation/lecture brute du prix (EP-002, consommé via son interface) ; hold/achat/annulation
eux-mêmes côté serveur (EP-003, consommé via son interface) ; session/login/logout (EP-005) ;
consoles organisateur/opérateur.

#### Assumptions
None beyond what EP-005 already establishes for the session boundary.

#### Open Questions
None beyond EP-005's epic-level OQ-000-1 (step-up trigger), which this epic's purchase screen would
need to honor once resolved.

## Capability CAP-012 - Reservation and Purchase Journey UI

Permet à un client authentifié de pré-réserver un siège, de suivre le compte à rebours jusqu'à
l'achat, et d'acheter avec une clarté totale sur le montant débité avant toute confirmation.

### References
- spec: vision-general-objective-fr.md:245-343 (Écrans 2, 3, 4)

### Description
Le client confirme une pré-réservation sur un siège choisi, suit son compte à rebours en direct
jusqu'à l'achat (avec heure d'expiration absolue et plafond de durée totale visibles), puis achète :
le montant exact est affiché avant tout débit, la confirmation exige une pression délibérée, sûre en
simple pression et au rechargement, et chaque état affiché indique explicitement si un montant a été
prélevé. Après succès, le billet et le reçu sont affichés avec le montant réellement débité.

## Capability CAP-013 - My Reservations and Cancellation UI

Permet à un client authentifié de consulter ses réservations passées et courantes, de récupérer un
reçu, et d'annuler une réservation confirmée pour un remboursement intégral.

### References
- spec: vision-general-objective-fr.md:344-362 (Écran 5)

### Description
Le client consulte ses réservations (événement, siège, statut, montant payé, références), re-télécharge
un reçu, et annule une réservation confirmée après une étape de confirmation qui énonce la
conséquence (libération du siège, remboursement intégral). Une annulation déjà effectuée ou une
double soumission affiche "déjà annulée" calmement, sans second remboursement.
